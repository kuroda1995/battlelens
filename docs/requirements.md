# BattleLens(仮称)要件定義書

最終更新日: 2026-09-16

## 1. 文書の目的

これまでの実装内容と、今後着手する範囲を一つの文書に整理する。学校課題としての提出物であると同時に、転職活動のポートフォリオとしても継続利用するため、進捗と技術的な意思決定の根拠をいつでも振り返れるようにしておく。

## 2. プロジェクト概要

### 2.1 背景
- 学校の課題として、指定の禁止技術(下記3.1)を使わずにゼロからアプリケーションを構築し、AWSにデプロイする。
- 提出後も個人の趣味・転職活動のポートフォリオとして継続利用する。
- 題材は対戦ゲームの個人的な対戦分析ツール(パーティ構築・ダメージ計算・立ち回り予測・勝率分析)。

### 2.2 目的
- パーティ構築(努力値・個体値・性格・持ち物・技構成)を保存・編集できるツールを段階的に作る。
- 技術選定の一つひとつについて、学校で習った技術との対比で「なぜその技術を選んだか」を面接で説明できる状態にする。

### 2.3 対象ユーザー
- 開発者本人(個人利用)。将来的に対戦仲間へ見せることも想定するが、現時点ではマルチユーザー機能は必須要件としない。

## 3. 制約条件

### 3.1 使用禁止技術
React / TypeScript / Vite / Tailwind CSS / Java / Spring Boot / Gradle / PostgreSQL

### 3.2 著作権・商標に関する方針
- アプリ名は「ポケモン」等の商標語を含まないオリジナル名(仮称: BattleLens)。
- 公式ロゴ・パッケージアート・キャラクタースプライト画像は使用しない。
- 種族名・技名・特性名等のデータは [PokéAPI](https://pokeapi.co/) から都度取得し、自前DBには複製しない(保存するのは「ユーザーが作成したパーティデータ」のみ)。
- 実装対象は努力値・個体値・タイプ相性・ダメージ計算式などの「ゲームメカニクス(数式・ルール)」であり、著作物の複製ではないという整理で進める。
- README・アプリ画面フッターに非公式ファンツールである旨の免責表示を明記済み。

## 4. 採用技術スタックと選定理由

| 領域 | 選定技術 | 学習済み技術 | 選定理由 |
|---|---|---|---|
| フロントエンドUI | Svelte | React | コンパイル時にDOM更新コードを生成する設計思想の違いを説明できる |
| 言語(フロント) | JavaScript + JSDoc | TypeScript | ビルド構成をシンプルに保ちつつ最小限の型ヒントを得る |
| バンドラ | Rollup(Svelte公式テンプレート標準) | Vite | dev serverと一体化したViteと異なり、バンドル設定を自分で組む経験を積む |
| CSS | 素のCSS + Open Props | Tailwind CSS | ユーティリティクラスに頼らないデザイントークン管理・コンポーネントスコープCSSの設計力を示す |
| バックエンド | Python + FastAPI | Java + Spring Boot | 型ヒント+Pydanticバリデーション、非同期対応、軽量さを対比説明できる |
| 依存関係/ビルド管理 | Poetry | Gradle | Pythonの依存解決・lockfile・パッケージングの仕組みを理解する |
| データベース | Amazon RDS for MySQL | PostgreSQL | 禁止技術対象外のRDBMSとして採用。RDBという枠組みは維持しつつ設計思想の違いを説明できる |
| ORM/マイグレーション | SQLAlchemy + Alembic | (Spring Data JPA + Flyway相当) | Python側でのORM設計・スキーママイグレーション管理の経験 |
| 認証(Phase4予定) | Amazon Cognito | Spring Security | マネージド認証サービスの利用経験 |
| インフラ構築 | AWS CDK (Python) | ー | Infrastructure as Codeの経験。バックエンドと同じ言語で統一 |
| コンピュート | EC2(素のインスタンス + systemd + Nginx) | ー | サーバー運用(OSセットアップ・プロセス常駐化・リバースプロキシ)の経験 |
| 配信/CDN | S3 + CloudFront | ー | 静的フロントエンド配信とAPIルーティングをCDN層で統合 |
| ネットワーク | VPC + セキュリティグループ + SSM Session Manager | ー | RDSのプライベート隔離、SSH鍵管理不要の運用設計 |
| 外部データ | PokéAPI(都度取得+軽量キャッシュ) | ー | ゲームの大量データを自前DBに複製しない設計判断 |

## 5. システム構成

### 5.1 リポジトリ構成
```
frontend/   Svelte + Rollup によるSPA
backend/    FastAPI + Poetry によるREST API
infra/      AWS CDK (Python) によるインフラ定義(コード作成済み・cdk synthで検証済み。cdk deployは未実施)
docs/       本書などのドキュメント
```

### 5.2 想定アーキテクチャ(コードは作成済み・実デプロイは未実施)
```
利用者 → CloudFront(HTTPS) ─┬─ S3(静的フロントエンド)
                             └─ /api/* → EC2(FastAPI, Nginx+systemd常駐)
                                            └─ RDS for MySQL(分離サブネット)
EC2の運用: SSM Session Manager(SSH鍵・22番ポート開放なし)
DB認証情報: ローカルファイル(infra/.db-password.txt、gitには含めない)にのみ保存
           ※無料利用枠に完全に収めるため、Secrets Manager(月$0.40程度)は不採用
予算アラート: AWS Budgetsで月$5・実績80%到達時にメール通知
```

### 6.2 Phase 1: パーティ構築MVP — 実装・ローカル検証済み(AWSデプロイは未実施)
- パーティ構築(最大6体): 種族選択(日本語名対応のPokéAPI検索)、持ち物、技構成(最大4つ、種族ごとの習得技から選択・タイプ別色分け・日本語表示)、特性(日本語表示)、性格(日本語表示)、努力値、個体値(デフォルト31・編集可)。
- **努力値は「ポケモンチャンピオンズ」独自仕様(0〜32段階、合計上限66段階)**。実機での実測値をもとに以下の計算式を特定した(`backend/app/calculations/stats.py`)。
  - 無補正 / 性格で上がりやすい方: 1段階につき内部加算値+2
  - 性格で上がりやすい方は、さらに最終値に従来シリーズと同じ×1.1の補正がかかる
  - 性格で上がりにくい方は、乗算補正(×0.9等)はかからない代わりに10・20・30段階目で増加が止まる(+0)
- 実数値(Lv.50)をその場で計算表示。プルダウン選択式(0〜32)で努力値を割り振れる(数値入力の上下クリック操作を避けるため)。
- パーティの保存・一覧・編集・削除。
- ローカル環境(SQLite代替DBでの動作確認 + pytest)で一連の機能が動作することを確認済み。
- 本番想定のRDS for MySQLでの動作確認、AWSへの実デプロイは未実施。

### 6.3 Phase 2: ダメージ計算機 — 実装・ローカル検証済み
- こうげき側・ぼうぎょ側を自由に選択(保存済みパーティに縛られない単体選択式)し、技を指定してダメージ範囲(最小〜最大、%表示)・確定数(何発で倒せるか)を算出する。
- 考慮する補正: タイプ相性(PokéAPIのタイプ相性表を取得)・STAB・急所・天候(はれ/あめ/すなあらし/ゆき)・トリックルーム(素早さ比較の反転)・主要な持ち物(こだわり系・いのちのたま・たつじんのおび・とつげきチョッキ・しんかのきせき)。
- 技はタイプ別に色分け・グループ化したカスタムドロップダウン(`MoveTypeSelect.svelte`)で選択(パーティ構築のわざ選択も共通化)。
- 計算ロジックは `backend/app/calculations/damage.py` に実装し、`stats.py` と同様に既知の数値でユニットテストを担保。

### 6.4 Phase 3: 相手の行動予測・簡易勝率推定 — 未着手(要件定義のみ)
- 既知の相手ポケモン情報(見えている技・特性・素早さ等)から、次のターンに取りうる行動の候補を洗い出す。
- 素早さ比較とダメージ期待値から、自分側の最適な選択肢を提示する簡易ヒューリスティックを実装する。
- 上記を用いた簡易的な勝率推定(モンテカルロ法などの軽量な近似)を検討する。

### 6.5 Phase 4: 認証・対戦ログ・CI/CD — 未着手(要件定義のみ)
- Amazon Cognitoによるログイン機能の追加。
- ユーザーごとのパーティ・対戦ログの保存。
- 実際の対戦結果を記録し、個人の勝率・傾向を分析する機能。
- GitHub ActionsによるCI/CD(テスト自動実行、EC2への自動デプロイ)。

### 6.6 Phase 5: 発展 — 構想段階
- 対戦ログを使った勝率予測モデルの高度化。
- CloudWatchによる監視・アラート。

## 9. 非機能要件

- **パフォーマンス**: PokéAPI由来のデータ(種族名・特性名・技名)はプロセス内メモリにキャッシュし、EC2の常駐プロセスである利点を活かして再取得を避ける。初回アクセス時のみ数秒〜十数秒のキャッシュ構築コストが発生する。
- **セキュリティ**: RDSはプライベートサブネットに配置しEC2からのみ到達可能にする。EC2の運用はSSM Session Manager経由とし、SSH鍵・22番ポート開放を行わない。DB認証情報はSecrets Managerではなく、無料利用枠に収めるためローカルファイル(gitには含めない)にのみ保存する方式にしている(コストとのトレードオフ。詳細はdocs/tech-stack-rationale.md参照)。
- **コスト**: 個人開発規模を想定し、t3.microクラスのインスタンス・NATゲートウェイ不使用・Secrets Manager不採用など、AWS無料利用枠に完全に収まるよう構成している。意図せず無料枠を超えた場合に気づけるよう、AWS Budgetsで月$5・実績80%到達時のメール通知アラートも設定済み。
- **保守性**: DBスキーマ変更はAlembicマイグレーションで管理し、実数値計算等の重要ロジックはpytestで担保する。
- **データ正確性**: 種族値等の基礎データはPokéAPI(本編ゲーム準拠)を用いるが、「ポケモンチャンピオンズ」は本編とステータスがリバランスされている場合があることが実機検証で判明した(例: マスカーニャのとくこう種族値が本編81に対しチャンピオンズでは70)。本編と異なることが確認できた種族は `backend/app/champions_data.py` の上書きテーブルに追記していく運用とする。未確認の種族は本編準拠の値のまま。

## 11. 既知の課題・リスク

- ローカル動作確認はSQLiteの一時DBで代用しており、本番想定のMySQL(RDSまたはDocker上のMySQL)ではまだ検証していない。
- `cdk synth`(設計図の生成のみ、AWSリソースは作られない)までは検証済みだが、実際の`cdk deploy`(EC2・RDS等の作成、課金発生)は未実施。特にEC2のUserDataスクリプトは実機での動作を未検証のため、初回デプロイ時に調整が必要になる可能性がある。
- 技・特性名の日本語キャッシュはプロセス内メモリのため、EC2再起動のたびに初回アクセスでキャッシュ再構築が発生する(数秒程度)。
- メガシンカ・ガラル/アローラのすがた等の「フォルム違い」は現状、日本語名検索の対象外(英語名のみ)。
- 「ポケモンチャンピオンズ」が本編と種族値をリバランスしている可能性があり、確認できた差分のみ `backend/app/champions_data.py` で個別に上書きしている(現状はマスカーニャのとくこうのみ確認済み)。他の種族についても実機で確認され次第、随時追加が必要。
