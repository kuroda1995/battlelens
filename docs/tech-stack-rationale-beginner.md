# 技術選定理由 やさしい説明書(初心者向け)

最終更新日: 2026-09-16

## この文書について

`docs/tech-stack-rationale.md` の内容を、専門用語をできるだけ使わずに、たとえ話でかみ砕いて説明し直したもの。まずはこちらで「感覚」をつかんでから、専門用語版を読むと理解しやすいはず。完璧に覚える必要はなく、人に説明するときに「たとえ話」を思い出せれば十分。

## そもそもの前提知識(先にここだけ読む)

- **フロントエンド**: ユーザーが実際に画面で見て触る部分。ボタンとか入力欄とか。
- **バックエンド**: 画面の裏側で、データを保存したり計算したりする部分。フロントエンドから「これ計算して」「これ保存して」とお願いされる係。
- **API**: フロントエンドとバックエンドが会話するときの「注文の仕方のルール」。レストランで言う「メニュー」みたいなもの。「この形式で注文すればちゃんと料理(データ)が出てくる」という約束事。
- **ライブラリ/フレームワーク**: 誰かが作ってくれた「便利な道具セット」。ゼロから全部自分で作らなくて済むように、よく使う部品をまとめてくれているもの。
- **ビルド**: 自分が書いたプログラムを、ブラウザやコンピュータが実際に動かせる形に「変換・組み立て」する作業。料理で言う「仕込み」に近い。
- **サーバー**: インターネット越しにアプリを動かし続けている、どこかの倉庫にあるコンピュータ。
- **デプロイ**: 自分のパソコンで作ったアプリを、誰でもアクセスできるようにサーバーに配置する作業。「お店を開店する」イメージ。
- **データベース(DB)**: データをきちんと整理して保存しておく、デジタルな倉庫(エクセルの表がたくさん集まったもの、と思ってもいい)。

## 1. Svelte(採用) vs React(禁止)

**たとえ話**
- React: 部屋の状態を毎回写真に撮って、前の写真と見比べて「あ、コップの位置が変わった」と気づいてから片付けるやり方。
- Svelte: 「コップを動かしたら、ここを拭く」という手順をあらかじめ紙に書いておいて、実際に動いたらその手順書通りに動くだけ、というやり方。

**かんたんに言うと**
Reactは「動いた後に、何が変わったかその場で調べて」画面を直す。Svelteは「あらかじめ、何が変わったら何をすればいいか」を先に用意しておくので、その場で調べる手間がない。

**なぜSvelteを選んだか**
学校で習ったReactとは違うやり方を実際に触ってみて、「画面の更新の仕方にはいろんな考え方があるんだ」ということを体験するため。

**覚えておきたいポイント**
Reactは世の中でとても多く使われていて、情報も仕事の求人も多い。Svelteはそれに比べるとまだ少数派。

## 2. JavaScript + JSDoc(採用) vs TypeScript(禁止)

**たとえ話**
- TypeScript: 容器ごとに「ここは牛乳専用」「ここは水専用」と決まっていて、間違った液体を入れようとすると物理的に入らない仕組み。
- JavaScript + JSDoc: 容器に「牛乳用」と付箋でメモを貼っているだけ。メモを見れば分かるけど、間違えて水を入れることも一応できてしまう。

**かんたんに言うと**
TypeScriptは「間違えたら教えてくれる」機能が強力。今回使ったJavaScript+JSDocという書き方は、そのメモ(ヒント)だけ書いておいて、チェックは緩め。

**なぜこちらを選んだか**
TypeScriptが禁止技術だったから。加えて、自分ひとりで作る小さいアプリなら、そこまで厳しいチェックがなくても何とかなるかを試したかった。

**覚えておきたいポイント(正直に)**
これは今回選んだ中で唯一、「本当はTypeScriptの方が優れている場面が多い」と正直に言える技術。特に、何人かで一緒に開発するときは、TypeScriptの「間違えたら教えてくれる」機能がとても役に立つ。もし会社に入って、みんなでコードを書くことになったら、迷わずTypeScriptを使う。

## 3. Rollup(採用) vs Vite(禁止)

**たとえ話**
プラモデルで言うと、Viteは「組み立て済み・塗装済みの完成品」。Rollupは「パーツを自分で1個ずつ組み立てるプラモデル」。実はViteの中身も、組み立てる部品としてRollupを使っている。

**かんたんに言うと**
どちらも「自分が書いたコードを、ブラウザが読める形にまとめる道具」。Viteは初めから便利機能がたくさん付いていて、Rollupはそれを自分で1つずつ設定して組み立てる必要がある。

**なぜRollupを選んだか**
Viteが「裏側で自動でやってくれていること」を、自分の手で設定してみることで、道具の中身を理解したかったから。

**覚えておきたいポイント**
Viteの方が今は圧倒的に使われていて、動作も速い。Rollupを直接使うのは、今では少し珍しいやり方。

## 4. 素のCSS + Open Props(採用) vs Tailwind CSS(禁止)

**たとえ話**
- Tailwind: レゴブロックのように、あらかじめ決まった形のパーツ(クラス)をたくさん組み合わせて家(見た目)を作る。
- 今回のやり方(Open Props): 「使っていい色の一覧」「使っていい余白の大きさの一覧」という見本帳だけをもらって、家具や壁は自分で1つずつ設計図(CSS)を書いて作る。

**かんたんに言うと**
CSSというのは「見た目を決めるための言語」。Tailwindは見た目の部品をあらかじめ大量に用意してくれる道具。今回は、色や余白の"ルール"だけを借りて、見た目そのものは自分で書いた。

**なぜこちらを選んだか**
Tailwindが禁止技術だったから。加えて、部品に頼らずCSSを自分の手で書く練習をしたかったから。

**覚えておきたいポイント**
Tailwindを使うと、見た目を考える時間をかなり短縮できる。今回のやり方は、その分自分で考えて書く量が増える。

## 5. Python + FastAPI(採用) vs Java + Spring Boot(禁止)

**たとえ話**
- Spring Boot: 「この人は受付係です」「この人は在庫係です」というラベル(アノテーション)を貼っておくと、会社の人事部(DIコンテナ)が勝手に配置・準備をしてくれる仕組み。
- FastAPI: 注文用紙のフォーマット(型ヒント)を決めておくと、そのフォーマット通りに書かれていない注文は自動ではじいてくれる仕組み。

**かんたんに言うと**
どちらも「バックエンド(裏側の処理)を作るための道具」。Spring Bootは「ラベルを貼ると自動で色々準備してくれる」やり方。FastAPIは「注文用紙のフォーマットを決めておくと、そのまま自動でチェックしてくれる」やり方。

**なぜFastAPIを選んだか**
Javaという言語ではなくPythonという言語で、Spring Bootとは違うやり方のバックエンドの作り方を経験するため。また、このアプリは外部のデータ(PokéAPIという他社のサービス)に何度も問い合わせる必要があり、FastAPIは「複数の問い合わせを同時に進める」のが得意な仕組みを持っているので、それも活かした。

**覚えておきたいポイント**
Spring Bootは大きな会社のシステムでよく使われていて実績が多い。FastAPIは比較的新しく、個人開発や小〜中規模のプロジェクトでよく使われる。

## 6. Poetry(採用) vs Gradle(禁止)

**たとえ話**
Gradleは「何でもできる万能工具箱」。Poetryは「材料(部品)を注文して、在庫を管理してくれる専門の道具」。

**かんたんに言うと**
プログラムを作るときは、他の人が作った部品(ライブラリ)をたくさん使う。その部品を「どのバージョンを、どこから持ってくるか」を管理するのがこの道具の役目。Pythonという言語には「コンパイル」という作業自体がないので、Gradleが持っている機能のうち「部品を集めて管理する」部分だけが必要で、それをPoetryが担当している。

**なぜPoetryを選んだか**
Pythonにおける部品管理の仕組みを理解するため。

**覚えておきたいポイント**
Gradleはもっと多機能(部品管理だけでなく、色々な自動作業もできる)。PythonにはGradleと同じ意味での「ビルド」という概念がないため、単純な1対1の置き換えではない。

## 7. Amazon RDS for MySQL(採用) vs PostgreSQL(禁止)

**たとえ話**
どちらも「データを表形式(エクセルの表のような形)で保存してくれる倉庫会社」。今回は禁止されていた倉庫会社(PostgreSQL)の代わりに、別の有名な倉庫会社(MySQL)を使った、というだけの話。

**かんたんに言うと**
基本的な使い方(データを表として保存して、後で検索する)はほとんど同じ。細かい内部の仕組み(データの保存方法や複製の方法)に違いがあるが、今回作ったアプリの規模では、その違いを意識する場面はまだ少ない。

**なぜMySQLを選んだか**
PostgreSQLが禁止技術だったから。有名で情報も多いMySQLを選んだ。

## 8. SQLAlchemy + Alembic(採用) vs Spring Data JPA + Flyway相当

**たとえ話**
- ORM(SQLAlchemyやJPA): プログラムの言葉と、データベースの言葉(SQL)を翻訳してくれる通訳さん。
- Alembic/Flyway: データベースの「模様替えの記録ノート」。いつ、どんな変更をしたかを順番に記録しておいて、誰の環境でも同じ順番で模様替えを再現できるようにする道具。

**かんたんに言うと**
プログラムの中で「パーティを保存して」と書くだけで、裏側で実際のデータベース向けの命令文(SQL)に翻訳してくれるのがORM。データベースの construction(テーブルの形)を後から変更したときの記録を管理するのがAlembic。

**なぜこちらを選んだか**
Pythonでのデータベースの扱い方(通訳の仕組みと、模様替えの記録の仕組み)を経験するため。

---

## 9. AWSアーキテクチャ: EC2 + RDS(サーバーレスではなくあえてこの構成)

**たとえ話**
- サーバーレス: 使った時間だけ電気代を払うレンタルスペース。誰かが電気の管理や建物の管理をやってくれる。
- EC2: 自分で借りて、自分で電源やエアコンの設定をする、1棟丸ごとのアパートの部屋。

**かんたんに言うと**
サーバーレスは「面倒な管理を全部お任せできる分、自分でコントロールできる部分は少ない」。EC2は「自分で設定する手間はあるけど、中の仕組みを全部自分の目で見て理解できる」。

**なぜEC2+RDSを選んだか**
今回は「サーバーを自分で組み立てて動かす経験をすること」自体が目的だったので、あえて手間のかかるEC2を選んだ。

**覚えておきたいポイント**
個人の小さいアプリを運用するだけなら、実はサーバーレスの方が管理も楽でお金もかからないことが多い。それでも今回はあえて「自分で管理する」経験を優先した。

## 10. AWS CDK(採用予定) vs 手動でポチポチ設定 / Terraform

**たとえ話**
- 手動設定: 家具屋さんに毎回口頭で「この場所にこの家具を置いてください」とお願いして組み立ててもらう。
- CDK: 「組み立て説明書」を先にプログラムとして書いておいて、その説明書通りに何度でも自動で組み立ててもらう。

**かんたんに言うと**
AWSの設定は、画面をマウスでポチポチ操作しても作れるが、それだと「どう設定したか」が記録に残らない。CDKを使うと、設定内容がぜんぶプログラムのファイルとして残るので、後から見返せるし、間違えたときにやり直しやすい。

**なぜCDKを選んだか**
インフラの設定も「プログラムのコードとして記録に残す」経験を積むため。バックエンドと同じPythonという言語で書けるのも理由の一つ。

## 11. SSM Session Manager(セキュリティのくふう)と、あえて見送ったSecrets Manager

**たとえ話**
- 従来のやり方: 合鍵を作って、それぞれの担当者に配って回る。合鍵をなくしたら大変。
- 今回のやり方(SSM): 合鍵を作らず、「AWSのアカウントの権限を持っている人だけ」がそのまま入れる仕組み(顔認証で入れるオフィスのイメージ)。これは無料。
- パスワードの扱い: 本来は「金庫(Secrets Manager)にしまっておいて、必要な人・必要なプログラムだけが開けられるようにする」のがお手本のやり方。ただし、この金庫サービスは無料枠の対象外で、月60円くらいの利用料がかかることが分かった。個人の学習用アプリを完全に0円に抑えたかったので、今回はパスワードを自分のパソコンにだけ保存しておいて、サーバーを作るときに直接渡す、という簡易的なやり方に変更した。

**かんたんに言うと**
「鍵を配らない」工夫はそのまま採用。「パスワードを金庫にしまう」工夫は、月60円というコストとの兼ね合いで、今回はあえて見送った。人数が増える本番のシステムだったら、迷わず金庫(Secrets Manager)を使う。

## 全部まとめて一言で言うなら

> 「学校で習った技術をあえて使わずに、それぞれ違う考え方の技術を選んで、実際に手を動かして比較しながら学んだ」

これだけ覚えておいて、聞かれた技術について「たとえ話」を思い出しながら話せれば十分。全部を完璧に説明できなくてもいい。分からないところを聞かれたら、正直に「そこはまだ勉強中です」と言うのも、変に知ったかぶりするよりずっと良い印象になる。
