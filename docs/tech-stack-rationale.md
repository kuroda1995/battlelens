# 技術選定理由 説明書

最終更新日: 2026-09-16

## この文書の使い方

これは提出・面接で「なぜこの技術を選んだのか」を自分の言葉で説明できるようになるための学習用資料。各技術について

1. **一言まとめ**(覚えるための短いフレーズ)
2. **技術的な違い**(何がどう違うのか、仕組みレベルで)
3. **選定理由**(なぜそれを選んだのか)
4. **正直なトレードオフ**(相手の技術が優れている点も認める。これがあるとハッタリに聞こえず、逆に信頼される)
5. **想定問答**(聞かれたときにそのまま使える回答例)

の順で書いている。丸暗記するのではなく、「技術的な違い」の部分を自分の言葉で説明できるようになることを目標にする。

## 全体方針(まず最初に言えるようにする一言)

> 「学校で習った技術の対義語・代替技術をあえて選ぶことで、UIライブラリ、型システム、バックエンドフレームワーク、DB、インフラ構築方法など、それぞれの領域で"設計思想の違う選択肢"を実際に手を動かして比較できるようにした」

これが全体を貫く一貫したストーリー。個別の技術の話をする前にこの一文を言えると、行き当たりばったりの選定ではなく意図した比較学習だと伝わる。

## 1. Svelte(採用) vs React(禁止)

**一言まとめ**: Reactは実行時に仮想DOMで差分計算、Svelteはビルド時にコンパイルして素のDOM操作コードを生成する。

**技術的な違い**
- React: コンポーネントが呼ばれるたびに仮想DOM(メモリ上のツリー)を再生成し、前回との差分(reconciliation)を計算してから実際のDOMに反映する。`useState`/`useEffect`などのHooksで状態と副作用を管理する。
- Svelte: コンパイラであり、`.svelte`ファイルをビルド時に解析して「どの変数が変わったらどのDOM操作をすべきか」を静的に埋め込んだJavaScriptを生成する。実行時に仮想DOMや差分計算のランタイムを持たない。`let`変数への再代入がそのままリアクティビティになる。

**選定理由**
- Reactの仮想DOM方式とは根本的に異なる「コンパイラ最適化」というアプローチを実際に触って理解するため。
- 生成されるバンドルにReact/ReactDOMのようなランタイムライブラリを含まないため、S3+CloudFrontでの静的配信と相性が良い(バンドルサイズが小さい)。

**正直なトレードオフ**
- Reactはエコシステム(ライブラリ・求人数・情報量)が圧倒的に大きく、実務での採用実績も多い。大規模開発でのNext.jsのようなフレームワーク統合や、TypeScript(TSX)との親和性もReactが強い。

**想定問答**
- Q. なぜReactを使わなかったのですか?
  A. 課題の制約に加え、Reactの仮想DOM(実行時差分計算)とは異なる、Svelteのコンパイル時最適化という設計思想を実際に体験したかったためです。実務でのシェアはReactが圧倒的に大きいと理解していますが、両方の仕組みを知ることでUI技術選定の引き出しを増やせると考えています。

## 2. JavaScript + JSDoc(採用) vs TypeScript(禁止)

**一言まとめ**: TypeScriptはビルド時に型を強制、JSDocはコメントで型のヒントを与えるだけの緩やかな仕組み。

**技術的な違い**
- TypeScript: `.ts`ファイルを書き、`tsc`(TypeScriptコンパイラ)が型チェックとJavaScriptへのトランスパイルを行う。型エラーがあればビルドが失敗する。
- JavaScript + JSDoc: 通常の`.js`ファイルに `/** @param {string} name */` のようなコメントで型情報を書く。エディタ(VS CodeのIntelliSenseなど)が任意でこれを読み取って補完・警告を出すが、ビルドを止める強制力はない。

**選定理由**
- 課題でTypeScript自体が禁止技術に指定されていたため。
- `tsconfig.json`やトランスパイル設定を増やさず、Rollupのビルド構成をシンプルに保てる。
- 個人開発・小規模スコープであれば、JSDocの緩やかな型ヒントでも開発体験を大きく損なわないことを確かめる意図もあった。

**正直なトレードオフ**(ここは一番"盛らずに"話すべき部分)
- チーム開発や中〜大規模なコードベースでは、TypeScriptの「ビルドを止める強制力」がリファクタリング時の事故を大きく減らす。JSDocはあくまで任意のヒントで、チェックをすり抜けるバグを防ぎきれない。
- 実務でチーム開発に入るなら、素直にTypeScriptを選ぶ。

**想定問答**
- Q. TypeScriptの方が良いのでは?
  A. おっしゃる通り、複数人開発や大規模なコードベースではTypeScriptの型安全性は大きな価値があります。今回は課題の制約と個人開発・小規模というスコープを踏まえ、JSDocによる軽量な型ヒントで十分と判断しました。実務でチーム開発するならTypeScriptを選びます。

## 3. Rollup(採用) vs Vite(禁止)

**一言まとめ**: Viteは「devサーバー+ビルドツール」が一体化した開発環境、Rollupは素のバンドラそのもの。

**技術的な違い**
- Vite: 開発時はネイティブESモジュールを使い、変更したファイルだけを都度ブラウザに配信することで高速なHMR(Hot Module Replacement)を実現する。本番ビルドは内部でRollupを呼び出している。
- Rollup: バンドラ単体。devサーバーやHMRの仕組みは標準で持たず、`rollup-plugin-svelte`・`@rollup/plugin-node-resolve`・`rollup-plugin-css-only`・`rollup-plugin-livereload`など、必要な機能をプラグインとして自分で組み合わせる。

**選定理由**
- Svelte公式テンプレート(`sveltejs/template`)が標準でRollupを採用しており、Viteが裏側で自動化してくれている「モジュール解決」「CSS抽出」「ライブリロード」を自分で設定することで、バンドラが何をしているかを理解できる。

**正直なトレードオフ**
- Viteは開発時の体験(起動速度・HMRの速さ)が優れており、現在のフロントエンド開発ではデファクトスタンダードになりつつある。プラグインエコシステムもVite向けの方が充実している。

**想定問答**
- Q. なぜViteではなくRollupですか?
  A. 課題の制約に加え、Viteが内部で使っているRollupを直接設定することで、モジュール解決やCSS抽出といったバンドラの基本的な仕組みを理解したかったためです。

## 4. 素のCSS + Open Props(採用) vs Tailwind CSS(禁止)

**一言まとめ**: TailwindはHTMLにユーティリティクラスを並べる方式、Open Propsは「デザイントークン(CSS変数)」だけを提供するライブラリで、実際のCSSは自分で書く。

**技術的な違い**
- Tailwind: `class="flex p-4 text-gray-700"`のように、あらかじめ用意された小さなクラス名を組み合わせてスタイリングする。ビルド時に使用しているクラスだけを抽出してCSSを生成する。
- Open Props + 素のCSS: Open Propsは色・余白・角丸・シャドウなどを`--gray-3`や`--size-4`のようなCSSカスタムプロパティとして提供するだけ。実際に`.card { padding: var(--size-4); }`のようなCSSクラスやSvelteのコンポーネントスコープCSS(`<style>`タグ)は自分で書く。

**選定理由**
- ユーティリティクラスに頼らず、CSSカスタムプロパティによるデザイントークン管理と、コンポーネント単位でスタイルを閉じ込める設計(Svelteのスコープ付きCSS)を実践するため。

**正直なトレードオフ**
- Tailwindはクラス名の命名で悩む時間を減らし、一貫したデザインシステムを高速に組み立てられる。大規模なUIやデザインシステムが確立しているチームでは、Tailwindの方が生産性が高いことが多い。

**想定問答**
- Q. なぜTailwindを使わなかったのですか?
  A. 禁止技術だったことに加え、ユーティリティクラスに頼らずCSSカスタムプロパティでデザイントークンを管理し、コンポーネントスコープCSSを直接書く設計力を示したかったためです。

## 5. Python + FastAPI(採用) vs Java + Spring Boot(禁止)

**一言まとめ**: Spring Bootはアノテーション+DIコンテナのフルスタックMVCフレームワーク、FastAPIは型ヒント+Pydanticで宣言的にバリデーションする非同期(ASGI)フレームワーク。

**技術的な違い**
- Spring Boot: `@RestController`や`@Autowired`などのアノテーションを使い、DI(依存性注入)コンテナがオブジェクトのライフサイクルを管理する。JVM上で動作し、静的型付け(コンパイル時チェック)。
- FastAPI: Pythonの型ヒント(`def create_party(payload: PartyIn)`)をそのままバリデーションルールとして使う(Pydantic)。Starletteをベースにした非同期(ASGI)フレームワークで、`async def`によるノンブロッキングI/Oがフレームワークレベルでサポートされている。

**選定理由**
- 「型ヒントを書くとそのままバリデーションになる」という宣言的なアプローチは、Spring Bootのアノテーション+DIとは異なる設計思想であり、比較して学べる。
- 本アプリはPokéAPIという外部APIへの問い合わせが多い(種族検索・技名の日本語化など)。`async/await`でI/Oを待っている間に他のリクエストを処理できる非同期処理の恩恵を実際に活かせる構成にした(`app/routers/species.py`で`asyncio.gather`による並列取得を実装)。
- 軽量で起動が速く、EC2 1台構成のような小規模インフラに向いている。

**正直なトレードオフ**
- Spring Bootは大規模エンタープライズでの実績が豊富で、DIコンテナによる疎結合設計や、コンパイル時の型チェックによる堅牢性で強い。FastAPI(Python)は動的型付け言語なので、型ヒントはあくまで実行時のバリデーションが中心であり、コンパイル時の網羅的なチェックはmypy等の別ツールに頼る必要がある。

**想定問答**
- Q. なぜSpring Bootを使わなかったのですか?
  A. 課題の制約に加え、非同期I/OをネイティブにサポートするPythonのASGIフレームワークを使うことで、Spring Bootのアノテーションベース設計とは異なる「型ヒント+Pydanticによる宣言的バリデーション」を経験したかったためです。実際に外部API(PokéAPI)への並列アクセスで非同期処理の恩恵を活かしています。

## 6. Poetry(採用) vs Gradle(禁止)

**一言まとめ**: GradleはJVMの「ビルド(コンパイル)+依存関係管理+タスクランナー」、PoetryはPythonの「依存関係管理+パッケージング」専用ツール。Pythonはインタプリタ言語なのでコンパイルの概念自体がない。

**技術的な違い**
- Gradle: `build.gradle`(Groovy/Kotlin DSL)に依存関係やタスクを定義し、コンパイル・テスト・パッケージングなど複数のタスクを柔軟に組み立てられるビルドツール。
- Poetry: `pyproject.toml`に依存関係を宣言し、`poetry.lock`で「誰の環境でも同じバージョンの依存関係が入る」ことを保証する。仮想環境の作成・管理も自動で行う。

**選定理由**
- Pythonにおける依存解決・仮想環境・lockファイルによる再現性の仕組みを理解するため。

**正直なトレードオフ**
- Gradleはタスクランナーとしての柔軟性(カスタムタスク、マルチモジュール構成、ビルドキャッシュ)が非常に強力。Poetryは依存関係管理に特化しておりシンプルな分、複雑なビルドパイプラインの構築には向かない。

**想定問答**
- Q. Gradleに相当するものは何を使いましたか?
  A. Pythonにはコンパイルという概念自体がないため、Gradleが担っていた役割のうち「依存関係管理・パッケージング・再現可能な環境構築」に相当する部分をPoetryが担っています。

## 7. Amazon RDS for MySQL(採用) vs PostgreSQL(禁止)

**一言まとめ**: どちらもRDBMSで基本的なSQL/ACID特性は共通。禁止技術がPostgreSQLだったため、代表的な代替RDBMSとしてMySQLを選んだ。

**技術的な違い(一般論として説明できるように)**
- MySQL: ストレージエンジン(InnoDBなど)がプラガブルで、バイナリログベースのレプリケーションが標準。
- PostgreSQL: 高度な型システム(JSONB型、配列型など)や豊富な拡張機能(PostGISなど)に強みがある。

**選定理由**
- PostgreSQLが禁止技術だったため、代替の主要RDBMSとしてMySQLを採用。RDBという枠組み自体は維持し、正規化されたテーブル設計(`parties` / `party_members` / `party_member_moves` の3テーブル)を実践した。

**正直なトレードオフ**
- 今回のデータモデルは単純な正規化テーブル構成であり、MySQLでもPostgreSQLでも実現できる範囲。PostgreSQL固有の高度な機能(JSONB等)を活かした設計ではない。

**想定問答**
- Q. なぜPostgreSQLではなくMySQLですか?
  A. 課題でPostgreSQLが禁止技術に指定されていたため、代替のRDBMSとしてMySQLを選びました。今回のデータモデルは基本的な正規化テーブル構成なのでどちらでも実現できますが、ストレージエンジンやレプリケーション方式の違いは今後の学習ポイントとして意識しています。

## 8. SQLAlchemy + Alembic(採用) vs Spring Data JPA + Flyway相当(禁止スタックの一部)

**一言まとめ**: JPA(Hibernate)はアノテーションからSQLを自動生成するフルスタックORM。SQLAlchemyはORM層とSQL生成層が分かれていて、生成されるSQLに近いところまでコントロールできる。マイグレーションはFlywayの代わりにAlembicを使う。

**技術的な違い**
- Spring Data JPA: `@Entity`アノテーションを付けたクラスから、Hibernateが自動でテーブル・SQLを生成する。リポジトリインターフェースを定義するだけでCRUDメソッドが使えるようになる。
- SQLAlchemy: 「Core(SQL Expression Language)」と「ORM」の2層構造。今回はORM層(`Mapped`/`mapped_column`)を使ってモデルを定義しているが、必要に応じて生SQLに近いレベルまで踏み込める柔軟性がある。
- Alembic: モデルの差分からマイグレーションスクリプトの雛形を生成し、リビジョン番号で順序管理する。Flywayの「バージョン付きSQLファイルを順番に適用する」という思想に近い。

**選定理由**
- Python側でのORM設計とスキーママイグレーション管理の経験を積むため。

**想定問答**
- Q. JPAとの違いは?
  A. JPAはアノテーションからHibernateが自動でSQLを生成するフルスタックORMですが、SQLAlchemyはCoreとORMの2層構造になっていて、生成されるSQLに近いところまでコントロールできる違いがあります。マイグレーションはFlywayと同じ思想のAlembicで、リビジョンベースにスキーマ変更を管理しています。

## 9. AWSアーキテクチャ: EC2 + RDS(サーバーレスではなくあえてこの構成)

**一言まとめ**: Lambda+DynamoDBのサーバーレス構成も検討したが、「サーバーを自分で構築・運用する経験」を優先してEC2+RDSにした。

**技術的な違い**
- サーバーレス(Lambda + API Gateway): リクエストが来た時だけ関数が起動する(コールドスタートあり)。OSやミドルウェアの管理はAWS側が行う。
- EC2 + RDS: 自分でOS(Amazon Linux)をセットアップし、Nginx(リバースプロキシ)・systemd(プロセス常駐化・自動再起動)・アプリケーションサーバー(Gunicorn+Uvicorn worker)を構成する。DBもRDSとして自分でインスタンスサイズやネットワーク(VPC・サブネット)を設計する。

**選定理由**
- 個人開発の学習目的として、サーバーレスの利便性の前に、まず「サーバーを自分で構築・運用する」経験(OSセットアップ、プロセス常駐化、リバースプロキシ設定、DBのネットワーク隔離)を積みたかった。

**正直なトレードオフ**
- サーバーレスはアイドル時のコストがほぼゼロで、スケーリングやOSパッチ適用の運用負荷もない。個人の小さなツールであれば、多くの場合サーバーレスの方が運用は楽になる。

**想定問答**
- Q. なぜサーバーレス(Lambda)ではなくEC2ですか?
  A. 個人開発の学習目的として、サーバーレスの利便性より先に「サーバーを自分で構築・運用する」経験(OSセットアップ、プロセス常駐化、リバースプロキシ設定)を積みたかったためです。将来的にサーバーレス構成も別途試してみたいと考えています。

## 10. AWS CDK(Python)(採用予定) vs 手動コンソール操作 / Terraform

**一言まとめ**: インフラをコードで管理する(IaC)経験を積むため、バックエンドと同じPythonで書けるCDKを選ぶ。

**技術的な違い**
- 手動コンソール操作: AWSマネジメントコンソールでポチポチ設定する。再現性がなく、変更履歴もGitで追えない。
- Terraform: HCLという専用の宣言的言語でインフラを記述する。マルチクラウド対応で業界標準の一つ。
- AWS CDK: Python(や TypeScript等)などの汎用プログラミング言語でインフラを記述し、内部でCloudFormationテンプレートに変換される。プログラミング言語の機能(ループ、条件分岐、クラス)がそのまま使える。

**選定理由**
- インフラをコードとして管理し、GitでレビューできるようにするというIaCの基本思想を実践するため。
- バックエンドと同じPythonで書けるため、言語を切り替えるコストがない。

**正直なトレードオフ**
- Terraformは実務での採用実績・求人数が非常に多く、マルチクラウド対応という強みもある。CDKはAWS専用。

**想定問答**
- Q. TerraformじゃなくてCDKですか?
  A. 会社によって採用するIaCツールは異なると理解していますが、まずは自分のバックエンドと同じPythonで「コードでインフラを定義する」経験を積むことを優先してCDKを選びました。Terraformも実務での採用実績が多いことは理解しており、今後学ぶ予定です。

## 11. VPC + SSM Session Manager(セキュリティ設計)とSecrets Managerを見送った理由

**一言まとめ**: SSH鍵を配らず22番ポートも開放しない設計は採用。DBの認証情報管理は、当初Secrets Managerを使う設計にしていたが、個人開発を完全に無料枠へ収めるためコスト面のトレードオフとしてあえて見送った。

**技術的な違い・選定理由**
- 従来の「SSH鍵で踏み台サーバーに接続する」運用は、鍵の紛失・漏洩やポート開放によるスキャン攻撃のリスクがある。AWS Systems Manager Session Managerを使うと、IAM権限だけでインスタンスにシェル接続でき、SSH鍵の配布や22番ポートの開放が不要になる。これは無料で使える。
- RDSの認証情報は、AWS Secrets Managerに自動生成させてEC2のIAMロールに読み取り権限だけを与える設計が一般的なベストプラクティス。実際に一度この構成で実装したが、Secrets Managerは無料利用枠の対象外で月$0.40程度の課金が発生することが分かった。個人の学習用プロジェクトを完全に無料枠内に収める判断を優先し、パスワードをローカル環境にのみ保存(gitには含めない)してデプロイ時にEC2へ直接渡す方式に変更した。

**正直なトレードオフ**
- 複数人が関わる本番システムであれば、月数十円のコストを理由にSecrets Managerを見送ることはまずない。パスワードのローテーションや監査ログ、アクセス制御の粒度といった点でマネージドサービスの方が明確に優れている。今回は「個人開発・単独所有・無料枠に完全に収める」という文脈だからこそ選んだ判断であり、状況が変われば迷わずSecrets Managerに戻す。

**想定問答**
- Q. セキュリティ面で工夫したことは?
  A. RDSをプライベートサブネットに隔離してEC2からのみ到達可能にし、EC2へのアクセスはSSH鍵を使わずSSM Session Manager経由にすることで、22番ポートの開放や鍵管理のリスクをなくしています。
- Q. DBの認証情報管理にSecrets Managerを使わなかったのはなぜですか?
  A. 最初はSecrets Managerを使う設計で実装しましたが、個人開発でコストを完全に無料枠へ収めたかったため、月$0.40程度の課金が発生するSecrets Managerをあえて見送り、パスワードをローカルにのみ保存してデプロイする方式に切り替えました。コストとセキュリティのトレードオフを意識した判断で、本番の複数人チームであればSecrets Managerを選びます。

## まとめ:一言で言えるように(覚え方の早見表)

| 技術 | 一言まとめ |
|---|---|
| Svelte | 仮想DOM(実行時)ではなくコンパイラ(ビルド時)でDOM更新コードを生成する |
| JS + JSDoc | ビルドを止める強制力はないが、個人開発の規模なら緩い型ヒントで十分と判断 |
| Rollup | Viteが裏でやっていることを自分で設定して理解する |
| Open Props | ユーティリティクラスではなくCSS変数でデザイントークンを管理する |
| FastAPI | アノテーション+DIではなく型ヒント+Pydanticで宣言的にバリデーションする非同期フレームワーク |
| Poetry | Pythonにはコンパイルがないので、Gradleの依存関係管理・パッケージングの部分だけに相当する |
| RDS MySQL | PostgreSQLが禁止だったための代替RDBMS。RDBの枠組みは維持 |
| SQLAlchemy+Alembic | JPAより生成SQLに近いところまで制御できるORM、Flyway相当のAlembicでマイグレーション管理 |
| EC2+RDS | サーバーレスより先に「サーバー運用そのもの」の経験を積む選択 |
| AWS CDK | バックエンドと同じPythonでインフラをコード化(IaC) |
| SSM Session Manager | SSH鍵を持たないセキュリティ設計。Secrets Managerは無料枠対象外だったため、コストとのトレードオフであえて見送った |

## よくある厳しい質問への心構え

- 「それって単に禁止されてるからでしょ?」→ 制約がきっかけであることは正直に認めた上で、「どうせ別の技術を選ぶなら、対極にある設計思想のものを選んで比較学習した」という一段深い意図を説明する。
- 「TypeScriptやTailwindの方が明らかに便利では?」→ 便利さを否定せず、「個人開発・小規模スコープだからこそ試せた判断であり、チーム開発ならTypeScript/Tailwindを選ぶ」と正直に答える。技術の優劣を絶対視せず、状況に応じた判断ができることを示す方が評価される。
